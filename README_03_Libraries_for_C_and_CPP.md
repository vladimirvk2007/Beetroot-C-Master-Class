# Питання 3. Бібліотеки, які можна підключити в C і C++

## Навіщо бібліотеки в embedded

Бібліотеки дозволяють не писати типові речі з нуля:

- контейнери;
- алгоритми;
- робота з протоколами;
- логування;
- тести.

У вбудованих системах важливо підключати не "будь-які" бібліотеки, а ті, що відповідають обмеженням target:

- RAM/Flash;
- deterministic поведінка;
- відсутність або жорсткий контроль heap;
- сумісність з компілятором і стандартом C/C++.

## Бібліотеки в C

### 1. Стандартна бібліотека C

- Заголовки: `stdint.h`, `stdbool.h`, `string.h`, `stdio.h`, `math.h` тощо.
- Дає базові типи, роботу з пам'яттю, рядками, математикою.

Примітка для embedded:

- Часто використовується лише частина стандартної бібліотеки.
- Деякі функції (`printf` з floating-point) можуть сильно збільшувати розмір прошивки.

### 2. CMSIS (для ARM Cortex-M)

- Низькорівневі визначення ядра, регістрів, interrupt-механізмів.
- Фактичний стандарт для ARM MCU проєктів.

### 3. Vendor HAL/LL

- ST HAL/LL, NXP SDK, Nordic SDK, ESP-IDF (C-орієнтовані API) тощо.
- Драйвери периферії: GPIO, UART, SPI, I2C, ADC, timers.

### 4. RTOS-бібліотеки (часто C API)

- FreeRTOS, Zephyr kernel API (частково C-підхід), ThreadX.
- Планувальник задач, черги, м'ютекси, таймери.

### 5. Протокольні стеки на C

- lwIP (TCP/IP), mbedTLS/wolfSSL (TLS), nanopb (Protobuf), cJSON.

## Бібліотеки в C++

### 1. Стандартна бібліотека C++ (обраний піднабір)

- Заголовки: `<array>`, `<algorithm>`, `<utility>`, `<type_traits>`, `<cstdint>`.
- Для embedded часто використовують "safe subset".

Примітка:

- `std::vector`, `std::string`, `std::map` можуть бути неідеальні без політики пам'яті.
- В середовищах з жорсткими обмеженнями часто переходять на fixed-capacity підходи.

### 2. ETL (Embedded Template Library)

- Фіксовані контейнери: `etl::vector`, `etl::array`, `etl::map`, `etl::string`.
- Підходить для deterministic embedded-архітектури.
- Не вимагає heap для більшості сценаріїв.

### 3. Бібліотеки для юніт-тестів

- Catch2, doctest, GoogleTest (здебільшого на host-side).
- Для embedded-проєктів часто тести запускають на ПК, а не на MCU.

### 4. C++ обгортки над C-бібліотеками

- RAII-обгортки для драйверів/дескрипторів/ресурсів.
- Дають безпечніший API поверх існуючого C-коду.

## Що спільного для C і C++

1. Можна змішувати мови в одному проєкті
- Наприклад: low-level драйвери на C, бізнес-логіка на C++.

2. C++ може викликати C через `extern "C"`

```cpp
extern "C" {
#include "driver_c_api.h"
}
```

3. Лінкер збирає все разом
- `.c` і `.cpp` компілюються окремо, потім лінкуються в один firmware-бінарник.

## Як обрати бібліотеку для embedded

Перевіряйте перед підключенням:

1. Сумісність із вашим компілятором/стандартом
- Наприклад, ваш toolchain може обмежуватися C++17.

2. Модель пам'яті
- Чи є dynamic allocation?
- Чи можна працювати без heap?

3. Розмір і продуктивність
- Вплив на Flash/RAM.
- Час виконання на цільовому MCU.

4. Ліцензія
- MIT, BSD, Apache 2.0, GPL та вимоги до комерційного використання.

5. Якість підтримки
- Активність репозиторію, issue tracker, релізи, документація, CI.

6. Портованість
- Чи працює на вашому RTOS/toolchain/архітектурі.

## Практичний набір для старту майстер-класу

### Якщо курс на C

- CMSIS + vendor HAL
- FreeRTOS (за потреби)
- lwIP (мережа, якщо потрібна)
- mbedTLS/wolfSSL (безпека, якщо потрібна)

### Якщо курс на C++ (embedded-friendly)

- `cstdint`, `array`, `algorithm` (базовий піднабір STL)
- ETL як основні контейнери
- C-драйвери/HAL + C++ обгортки
- doctest/Catch2 для host-side тестів

## Висновок

- У C екосистема для embedded дуже зріла на рівні HAL/RTOS/stack.
- У C++ головний плюс це безпечніші та масштабованіші абстракції.
- Найпрактичніший підхід: комбінувати C і C++ залежно від шару системи.
