# Питання 5. Вивід даних: printf (C) проти std::cout (C++)

## Чому це важливо в embedded

Вивід даних у вбудованих системах потрібен для:

- діагностики та дебагу;
- логування станів і помилок;
- перевірки телеметрії.

Але будь-який механізм виводу впливає на:

- розмір прошивки (Flash);
- використання RAM;
- час виконання;
- детермінізм.

## `printf` у C (і C++)

### Плюси

- Простий і звичний форматований вивід.
- Широко підтримується на різних toolchain.
- Зручно швидко друкувати числа/рядки одним викликом.

### Мінуси

- Форматні рядки не типобезпечні.
- Помилка у `%d/%u/%f/%s` може дати некоректний вивід або UB.
- Підтримка float у `printf` часто сильно збільшує бінарник.

### Приклад

```c
int temp = 25;
printf("Temp = %d C\n", temp);
```

## `std::cout` у C++

### Плюси

- Типобезпечний вивід через оператор `<<`.
- Краща інтеграція з C++ типами.
- Менше ризику форматних помилок порівняно з `printf`.

### Мінуси

- Може бути важчим за розміром і runtime overhead у constrained target.
- Іноді потребує тонкого налаштування стандартної бібліотеки.
- На MCU без повної libstdc++ може бути незручним.

### Приклад

```cpp
int temp = 25;
std::cout << "Temp = " << temp << " C\n";
```

## Практичне порівняння

1. Типобезпека
- `printf`: нижча (форматний рядок + аргументи мають збігатися вручну).
- `std::cout`: вища (компілятор перевіряє типи в `<<`).

2. Розмір прошивки
- `printf`: часто легший у мінімальному режимі, але float може різко збільшити розмір.
- `std::cout`: часто важчий через iostream інфраструктуру.

3. Продуктивність
- Обидва можуть бути повільними на повільних UART при частому логуванні.
- Вузьке місце зазвичай транспорт (UART/SWO/semihosting), не лише API.

4. Зручність форматування
- `printf`: сильний у форматуванні через `%`-специфікатори.
- `std::cout`: гнучкий через потоки та маніпулятори (`std::hex`, `std::dec`).

## Embedded-нюанси

### 1. Вивід float

- У багатьох newlib/newlib-nano конфігураціях float у `printf` вимкнений за замовчуванням.
- Увімкнення float support може додати значний розмір у Flash.

### 2. Blocking I/O

- І `printf`, і `cout` часто блокують потік виконання, якщо вивід іде в UART.
- Для real-time ділянок коду логування треба обмежувати або буферизувати.

### 3. ISR контекст

- Не рекомендується викликати `printf`/`cout` з ISR.
- Краще ставити короткий event/flag і логувати в task/main loop.

## Рекомендації для майстер-класу

1. Для low-level embedded дебагу
- Починати з `printf` (простий і зрозумілий старт).

2. Для C++-орієнтованого коду
- Можна показати `std::cout` як типобезпечний варіант, але пояснити overhead.

3. Для production-проєкту
- Робити власний lightweight logger (рівні логів, буфер, compile-time enable/disable).
- Уникати зайвого виводу в критичних ділянках.

## Мінімальний lightweight-підхід (ідея)

```c
// C/C++ friendly macro wrapper
#ifdef DEBUG
  #define LOG_INFO(fmt, ...) printf("[I] " fmt "\n", ##__VA_ARGS__)
#else
  #define LOG_INFO(fmt, ...) do {} while (0)
#endif
```

Такий підхід дозволяє вимкнути логування на релізній збірці без зміни прикладного коду.

## Висновок

- `printf` зазвичай простіший і практичніший для bare-metal старту.
- `std::cout` безпечніший типово, але часто важчий для MCU.
- В embedded вибір роблять за бюджетом Flash/RAM, вимогами до real-time і політикою логування.
