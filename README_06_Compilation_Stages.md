# Питання 6. Етапи компіляції програми

## Загальна картина

Перетворення коду в готовий виконуваний файл проходить через кілька етапів.
Для C і C++ pipeline майже однаковий, різниця переважно у front-end компілятора.

Типовий ланцюжок:

1. Препроцесинг (Preprocessing)
2. Компіляція (Compilation)
3. Асемблювання (Assembling)
4. Лінкування (Linking)
5. Post-build кроки (особливо в embedded)

---

## 1. Препроцесинг

### Що відбувається

Препроцесор обробляє директиви:

- `#include` — вставляє вміст заголовків;
- `#define` — робить текстові підстановки;
- `#if/#ifdef/#ifndef` — умовно включає/виключає фрагменти коду.

Результат: "розгорнутий" текст програми без препроцесорних директив.

### Чому це важливо

- На цьому етапі формується фактичний код, який побачить компілятор.
- Багато "дивних" помилок спричинені саме макросами або include-конфліктами.

### Типова команда

```bash
g++ -E main.cpp -o main.ii
```

- `-E` зупиняє процес після препроцесора.
- Для C зазвичай: `gcc -E main.c -o main.i`.

---

## 2. Компіляція

### Що відбувається

Компілятор аналізує препроцесований код:

- синтаксис;
- типи;
- семантику;
- оптимізації високого рівня.

Після цього генерується асемблерний код (`.s`).

### Чому це важливо

- Саме тут з'являються більшість помилок C/C++ (типи, template, constness, тощо).
- Оптимізації (`-O0`, `-O2`, `-Os`) впливають на швидкість та розмір бінарника.

### Типова команда

```bash
g++ -S main.cpp -o main.s
```

- `-S` зупиняє процес після генерації асемблера.

---

## 3. Асемблювання

### Що відбувається

Асемблер перетворює `.s` у машинний object-файл:

- `.o` (Linux/embedded)
- `.obj` (часто у Windows toolchain)

Object-файл ще не є готовою програмою, бо містить нерозв'язані зовнішні символи.

### Чому це важливо

- Кожен `.c/.cpp` компілюється в окремий object.
- Це основа інкрементальної збірки (перекомпілюються лише змінені модулі).

### Типова команда

```bash
g++ -c main.cpp -o main.o
```

- `-c` означає: скомпілювати до object, без лінкування.

---

## 4. Лінкування

### Що відбувається

Лінкер об'єднує:

- object-файли (`main.o`, `adc.o`, ...);
- статичні/динамічні бібліотеки;
- startup-код і системні runtime-компоненти.

Лінкер розв'язує зовнішні символи (хто де реалізований) і формує фінальний файл:

- `.exe` на host;
- `.elf` для embedded/крос-компіляції.

### Чому це важливо

- Помилки на кшталт `undefined reference` виникають тут.
- Linker script в embedded визначає розкладку пам'яті (Flash/RAM секції).

### Типова команда

```bash
g++ main.o adc.o -o app.exe
```

Або в один крок (compile + link):

```bash
g++ main.cpp adc.cpp -o app.exe
```

---

## 5. Post-build (embedded)

### Що відбувається

Після створення `.elf` часто виконують:

1. Генерацію `.hex` або `.bin`
2. Перевірку розміру секцій (`text/data/bss`)
3. Прошивку на MCU
4. Створення map-файлу для аналізу пам'яті

### Типові команди

```bash
arm-none-eabi-objcopy -O ihex firmware.elf firmware.hex
arm-none-eabi-objcopy -O binary firmware.elf firmware.bin
arm-none-eabi-size firmware.elf
```

---

## Як це виглядає на прикладі одного модуля

Нехай є `main.cpp` і `adc.cpp`:

1. `main.cpp -> main.o`
2. `adc.cpp -> adc.o`
3. `main.o + adc.o + libs -> firmware.elf`
4. `firmware.elf -> firmware.hex/bin`

---

## Де шукати помилки по етапах

1. Препроцесинг
- проблеми з `#include`, макросами, include guards.

2. Компіляція
- синтаксис, типи, невірне використання API.

3. Асемблювання
- рідко явні помилки, зазвичай похідні від попереднього етапу.

4. Лінкування
- `undefined reference`, дублікати символів, несумісні бібліотеки.

5. Post-build
- помилки objcopy/flash tool, перевищення пам'яті target.

---

## Різниця C і C++ у pipeline

Pipeline однаковий, але:

- C++ має складніший етап компіляції (класи, шаблони, перевантаження);
- C++ частіше дає довші діагностики компілятора;
- у C++ можуть бути додаткові runtime-компоненти (за налаштувань toolchain).

---

## Висновок

Розуміння етапів компіляції дозволяє швидше діагностувати помилки, краще контролювати розмір прошивки та впевнено працювати з C/C++ toolchain у embedded-проєктах.
